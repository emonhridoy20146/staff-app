# 08 — Decisions (staff-app)

System-wide ADRs and open decisions: `field-api/docs/08-decisions.md` (notably ADR-007 sync protocol, ADR-009 background location, ADR-012 receipt numbers, ADR-014 tiles).

### ADR-M01 Flutter, Android first · fixed
- **Reason:** fixed decision; one codebase keeps iOS possible; good performance on low-end Android with Skia/Impeller.
- **Alternatives rejected:** native Kotlin (best background control but slower to build UI, no iOS path); React Native (weaker offline DB/background story for this case).

### ADR-M02 drift (SQLite) + SQLCipher for the local database · accepted
- **Reason:** relational queries (filters, joins, FTS5 search), reactive streams, typed migrations with schema tests, encryption.
- **Alternatives rejected:** Isar (maintenance uncertainty), Hive (no queries/joins, weak for 2,000+ rows with filters), ObjectBox (good speed, less SQL flexibility, licence considerations for sync), sqflite raw (no type safety).

### ADR-M03 Riverpod 2 + go_router · accepted
- **Reason:** compile-safe DI and state, testable without widgets, good with streams from drift; go_router for deep links from notifications.
- **Alternatives rejected:** Bloc (more boilerplate; fine but heavier for AI-generated code consistency), GetX (global magic, hard to test), Provider (superseded by Riverpod).

### ADR-M04 API client: generated Dart client from openapi.yaml · accepted
- **Reason:** contract owned by field-api; generation avoids drift.
- **Alternative kept:** hand-written freezed models validated by fixture tests if generator output is poor for some schemas (`oneOf`/nullable). Decision per schema documented in `packages/field_api_client/README.md`.

### ADR-M05 flutter_map for OSM tiles · accepted
- **Reason:** Leaflet-like API, TileProvider-agnostic, tile caching plugin, no Google dependency.
- **Alternatives rejected:** google_maps_flutter (only if OD-19 proves necessary), maplibre_gl (vector tiles, heavier native dependency — reconsider with PMTiles vector in P4).

### ADR-M06 Local notifications for promise reminders · accepted
- **Reason:** must work offline at 09:00 on the promised date; FCM only as backup.

### ADR-M07 Hold-to-confirm for money submission · accepted
- **Reason:** prevents accidental double taps and pocket taps; gives a deliberate moment while the customer watches.
- **Alternative rejected:** confirmation dialog (users tap through dialogs automatically).

### ADR-M08 UI never calls the network directly · accepted
- **Reason:** offline-first guarantee; all writes go through local DB + outbox; reads from DB streams.
- **Exception:** explicitly online-only actions (handover decision, on-demand balance refresh, password change) via use cases that show "internet required".

### Amendments made during the build (2026-11-15)
- **ADR-M02 amended:** encryption uses SQLite3MultipleCiphers (`sqlite3` package build hook `source: sqlite3mc`, `PRAGMA key`) instead of the separate SQLCipher plugin. Same at-rest protection; one native library; key = random 256-bit, stored in Android Keystore (`flutter_secure_storage`).
- **ADR-M03 amended:** Riverpod 3 (current stable) without code generation; `StateProvider` from `legacy.dart` only for simple UI state. go_router 18 with a stage-driven redirect (`lib/app/router.dart` `redirectFor`, unit-tested).
- **ADR-M04 interim:** until field-api publishes a stable generated Dart client, models are hand-written in `lib/core/api/api_models.dart` (only the fields the app reads) and every call goes through `FieldApi`. Replace with the generated package when available; do not mix.
- **ADR-M09 Dhaka time as fixed UTC+6:** Bangladesh has no DST; `core/time/clock.dart` uses a fixed offset instead of the tz database for business dates (the tz database is used only for scheduling local notifications).
- **ADR-M10 Demo mode:** `APP_ENV=demo` (the default build) runs entirely in memory against `FakeFieldApi` (a dio adapter implementing the contract routes the app uses) with 36 Barishal sample customers. Prod builds refuse demo mode at start-up. Used for UI review before field-api is deployed and for tests.
- **Location plugin:** decided 2026-11-15 (OD-M06): free now, paid possible later via admin setting. See ADR-M11.
- **ADR-M11 Switchable tracking provider · accepted (2026-11-15):** tracking goes through `TrackingProvider` (`lib/core/location/tracking/`). `FreeTrackingProvider` (geolocator with an Android foreground service) ships now; `PaidTrackingProvider` is a stub reporting `isAvailable = false`. The server setting `location.trackingProvider` (`free` | `paid`) is read at runtime and the tracker switches without an app update **if the installed APK contains the paid SDK**. A paid SDK cannot be downloaded at runtime: enabling it needs (1) buying the licence for app id `bd.howlader.staff_app`, (2) adding the plugin and implementing `PaidTrackingProvider`, (3) the licence key as a CI secret (`LOCATION_LICENSE_KEY`, never in the repo), (4) shipping that APK. After that the admin setting switches freely. Until then `paid` falls back to free, shown on the Me tab and in the heartbeat.
- **Attendance photo · decided by owner (2026-11-16):** a front-camera photo is required at work-in, break start, break end and work-out by default; which events need it is the server setting `attendance.selfieEvents` with master switch `attendance.selfieRequired` (contract 1.8.0). Amends field-api OD-12 (optional at work-in, off by default). Implemented with a `held` outbox state so attendance works offline and stays in order.
- **Co-work · decided by owner (2026-11-16), contract field-api 1.9.0:** staff of one branch can work together for a business day. Asking, accepting, rejecting and leaving are online-only (an ADR-M08 exception like handovers): a partner must see the answer at once, and a queued "accept" could land after the group ended. The session itself is stored on the phone, so joint visits are recorded offline with `coWorkSessionId`; the server decides who took part (members accepted at check-in) and gives each participant visit credit, weighted for targets by `cowork.visitCredit`. Money is never shared: collections and cash count only for the recorder. A joint visit stays one record by the recorder; partners see it on pull. The visit screen's co-work switch is on by default when a partner has accepted, because joint work is the reason the group exists; the staff can turn it off for a visit made alone.
- **Targets and reports in the app · 2026-11-17, contract field-api 1.10.0:** my daily target comes with every pull (dated record, personal or branch; working-day aware) and is cached, so Today's progress works offline; the old branch settings `dailyTargetPoisha` / `dailyVisitTarget` are dropped. Visit progress uses visit credit (single + co-work × `cowork.visitCredit`) computed on the phone; the server's monthly figure is the official one. My month and the leaderboard are read online (server-computed, ADR-M08 exception); the last month answer is cached for offline reading with its time. The leaderboard is shown to staff only when the admin turns it on (OD-15, default off); the app hides the entry and also handles the server's 403.
- **ADR-M13 Map pins, applied at once when missing · decided by owner (2026-11-17), contract field-api 1.11.0:** the pin screen is a map with a fixed centre pin instead of "stand at the door and send your GPS fix": staff often learn the place from the customer by phone or from a shared location, and the old 30 m GPS rule made pins hard to set. The point under the pin is sent as `method: map`; the phone's own fix goes along as `deviceGeo` so the manager can judge (field-api ADR-031). Owner decision (decision card): a pin for a customer with no usable location is set at once; moving an existing pin still needs a manager; branch setting `customers.staffPinApproval` (`when_missing` | `always`). A fake phone location never applies at once. The photo is optional for map pins (camera only, as before). The app predicts the outcome from the cached setting and the local customer only to word the screen; the server decides, and its `approved` push result and the customer change on pull are what the app shows afterwards. No optimistic local pin: the pin appears with the sync that sends it.
- **ADR-M14 Notices offline, leave online · owner request (2026-11-17), contract field-api 1.12.0 (field-api ADR-032):** "পড়েছি" on a notice is a field action like any other: it is saved on the phone and sent as the `broadcast_ack` mutation carrying the tap time, so a staff member without signal can still confirm, and the office sees when it was read, not when it synced. A pull that still says "not read" never overwrites a queued tap. Asking for leave and withdrawing it are online-only (an ADR-M08 exception like co-work): the server checks overlap with my other requests and tells my manager at once, and a request queued for days could be approved after its days have passed. The phone checks the form first (dates, 31 days, overlap with what it knows) and keeps the last list, holidays and my shift for offline reading with their time. A guarantor call is logged like a customer call with `target: guarantor`; the guarantor's number is read from the ERP data on the phone and is never stored in the call log or sent.
- **ADR-M15 The real ERP shape on the phone · 2026-11-18, contract field-api 1.13.0 (field-api ADR-033):** the production Laravel ERP is not changed; the app follows its data. One plan is one ERP invoice (installment or credit). The phone keeps what the ERP sends and only hides what the office does not see: lines the ERP rolled forward (amount 0) are hidden with a count, and returned or cancelled invoices are shown last and never offered for collection. The ERP takes one payment per installment invoice per day (OD-27, default No), so the collect flow warns when the chosen invoice already has a payment today, from the ERP data on the phone or from this phone's own collections; it never blocks, because a field collection is never dropped (field-api ADR-018) and the server makes it a conflict for the office. The ERP risk grade is shown read-only beside our own status badges; it never changes priorities or filters on the phone. Schema 7 adds only nullable or defaulted columns, so a pull fills them and nothing queued is touched.
- **ADR-M16 Committed live config with public values only · owner request (2026-11-18):** the owner wants to `git pull` and build in Android Studio against the live field-api without typing flags. `config/live.env` (outside the git-ignored `.env.*` pattern) is committed with the live test server's public URL, `APP_ENV=staging` (the server is the field-api test deployment, field-api ADR-034) and `API_MODE=live`; the shared run configurations in `.run/` pass it with `--dart-define-from-file`. Secrets (Sentry DSN, tracking licence key, signing keys) still go only in git-ignored `.env.*` files or CI secrets, and the app never holds an ERP credential because it never talks to the ERP. `test/core/live_config_test.dart` fails CI if a committed config gains another key, anything that looks like a secret, a non-HTTPS URL or an ERP address. A build with no defines stays the demo (ADR-M10), so a plain `flutter run` or *Build → Flutter → Build APK* never writes test data to a server connected to the production ERP by accident. When production gets its own domain, add `config/prod.env` the same way.
- **ADR-M12 No background location permission · accepted (2026-11-15):** tracking is a visible foreground service started while the app is open (work-in), so `ACCESS_BACKGROUND_LOCATION` is not requested ("While using the app" is enough). Trade-off: after a phone reboot tracking restarts only when the staff opens the app.
